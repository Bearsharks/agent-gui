You are writing one compact turn-history memo for future Codex self-improvement review.

Return ONLY one JSON object. Do not return markdown, bullets, comments, or prose.

The hook will inject schema_version, ts, and turn_id into the turn record, and will store session_id and cwd in session metadata. Do not include any of those hook-owned fields.

Allowed output fields, all required strings:
- user_intent: What the user actually wanted in this turn. Mention explicit limits such as "do not implement", "investigate only", "be concise", or "verify first".
- user_decisions: Decisions the user made or accepted, especially design, workflow, model, storage, schema, or scope decisions. Leave empty when none.
- user_corrections: Corrections, objections, or direction changes the user gave to the agent. Leave empty when none.
- memory_requests: Anything the user explicitly or implicitly asked the agent to remember for future behavior. Leave empty when none.
- agent_workflow: What the agent actually did, in workflow order. Distinguish investigation, explanation, review, command execution, implementation, verification, install, commit, and push.
- troubleshooting: Problems encountered while working, plus cause, response, and result when known. Leave empty for one-off environment noise without a useful handling pattern.
- agent_issues: Agent mistakes, missed expectations, repeated friction, or misunderstanding. Leave empty when none.
- successful_patterns: Reusable working patterns from the turn. Do not write generic praise; only include behavior worth repeating.
- lesson_candidate: A short reusable lesson that could become a skill rule. Leave empty for one-off or project-specific context.
- evidence: A short quote or close paraphrase of the most important user correction, decision, memory request, or preference. Prefer user wording over agent summary. Redact secrets and private data. Leave empty when no evidence matters.

Rubric:
1. Separate user judgment from agent judgment. Do not mix user decisions with agent conclusions.
2. Put user corrections, prohibitions, preferences, and memory requests in their dedicated fields.
3. Keep the memo short; one or two sentences per non-empty field is enough.
4. Evidence should be user wording or a very close paraphrase, not the agent's proposal unless that proposal was explicitly accepted.
5. Successful patterns must be reusable working behavior, not generic praise like "explained clearly".
6. Troubleshooting should include cause, response, and result when known; ignore transient noise unless it teaches a retry or setup pattern.
7. Do not overlearn from environment-dependent failures, missing binaries, unconfigured credentials, or transient errors.
8. Never write a durable negative claim like "tool X does not work"; if useful, capture the fix or retry pattern instead.
9. Do not store secrets, tokens, credentials, or raw private data.
10. Use Korean when the turn context is Korean.
11. If uncertain, use an empty string rather than inventing a lesson.
